# 2PeachGPT — RAG по техническим книгам

Учебный проект для ДЗ OTUS «Enterprise Private GPT». Вместо предложенного корпуса корпоративных документов используются три книги о генеративном ИИ, RAG и LangChain. Система ищет фрагменты, передаёт их языковой модели и показывает ответ с источниками и PDF-страницами.

**Текущая конфигурация:** эмбеддинги `BAAI/bge-m3` и Chroma работают локально; для генерации используется Qwen или YandexGPT через Yandex AI Studio в зависимости от `YC_MODEL_ID`. Python-бэкенд и веб-интерфейс работают локально. 

## Соответствие требованиям ДЗ

### Пункт 1. Модель и окружение

Задание допускает Яндекс.Облако как альтернативу локальному развёртыванию. Сознательно выбран этот вариант: обработка PDF, поиск и генерация проверены через единый OpenAI-совместимый API. С локальной LM делать не стал. Модель переключается через `YC_MODEL_ID` в корневом `.env` без изменения RAG-цепочки. Подключение реализовано в [src/llm.py](src/llm.py), параметры читаются в [src/config.py](src/config.py).

Сначала проверена `yandexgpt-5.1`, затем использована `qwen3.6-35b-a3b` через Yandex AI Studio. [src/check_llm.py](src/check_llm.py) отправляет короткий запрос и выводит ответ в консоль; более содержательные ответы обеих моделей сохранены в [отчёте](docs/evaluation.md). Это **проверка сетевого API** ( в том числе и изза последних проблем  Яндекс  Клауд по известной причине).

Локально развёрнуты Python-окружение через `uv`, модель эмбеддингов BGE-M3 и база Chroma. Секреты облачного доступа хранятся в `.env`, который исключён из Git. Инструкция по восстановлению окружения приведена [ниже](#установка-и-подготовка-базы).

### Пункт 2. Документы, чанкирование и векторная база

**Корпус.** Вместо тестовых корпоративных документов использованы три русскоязычные технические книги. Такой корпус позволяет проверить поиск по реальному содержанию и в дальнейшем расширить проект для личной библиотеки, не публикуя исходные PDF. 

PDF остаются локально в `data/raw/private/`. [Загрузчик](src/ingestion/pdf_loader.py) сохраняет в метаданных название файла и номер PDF-страницы, чтобы показывать проверяемый источник ответа.

**Извлечение текста и OCR.** Сначала текст извлекался через PyMuPDF. У книги «Генеративный ИИ на практике» текстовый слой пропускал видимые русские абзацы, поэтому для неё выполнено однократное распознавание Tesseract (`rus+eng`, 200 dpi) в [src/prepare_ocr.py](src/prepare_ocr.py). Результат сохраняется постранично в локальном JSONL и повторно используется загрузчиком. Остальные две книги читаются напрямую. Порог 80 символов в отчёте о PDF помогает находить подозрительно короткие страницы, но не удаляет их автоматически. После OCR в индекс попало больше текста первой книги; буквальная точность кода из OCR не гарантируется.

**Чанкирование.** [src/processing/chunker.py](src/processing/chunker.py) использует LangChain `RecursiveCharacterTextSplitter`: `chunk_size=1000`, `chunk_overlap=150`, оба значения **в символах**. Эти параметры приняты как первая рабочая гипотеза для технического текста: разделители сначала стараются сохранить абзацы и строки, затем режут более мелкие фрагменты; перекрытие удерживает часть контекста на границе чанков. Это не результат доказанной оптимизации. Чанки наследуют `source` и `page`, получают номер внутри страницы, параметры разбиения и стабильный ID для повторной индексации. Влияние `Top-K=3` и `Top-K=5` на поиск ответа проверено отдельно; размеры чанков в этом опыте не сравнивались — результаты в [отчёте](docs/evaluation.md).

**Эмбеддинги и база.** Для русского корпуса выбрана мультиязычная `BAAI/bge-m3`: она создаёт векторы размерности 1024 локально и используется с нормализацией. [Проверка](src/check_embeddings.py) дала большую близость вопроса «Что такое RAG?» к фразе о RAG (**0.493**), чем к фразе о яблочном пироге (**0.211**). Это простая проверка направления поиска, а не полноценный бенчмарк моделей. В [src/index_documents.py](src/index_documents.py) эмбеддинги чанков вместе с текстом и метаданными сохраняются в локальную [Chroma](src/storage/chroma_store.py); проверено 2850 записей. Chroma выбрана для первого индекса такого размера, поскольку она работает в каталоге проекта без отдельного сервера. 

Числа по каждой книге, ограничения OCR и путь хранения индекса приведены в разделе [«Корпус и индекс»](#корпус-и-индекс).

### Пункт 3. Сборка RAG-пайплайна

Все четыре шага выполняются в консольном сценарии [src/rag_cli.py](src/rag_cli.py); функция одного запроса есть в [src/rag.py](src/rag.py). Веб-сервер реализует ту же последовательность отдельно в [rag_server.py](rag_server.py), используя общие модули подключения к базе и модели.

1. **Векторизация вопроса.** `HuggingFaceEmbeddings` загружает локальную `BAAI/bge-m3` с нормализацией векторов. При вызове `similarity_search` или `similarity_search_with_score` LangChain вычисляет эмбеддинг вопроса. Подключение к коллекции описано в [src/storage/chroma_store.py](src/storage/chroma_store.py).
2. **Семантический поиск Top-K.** [src/rag_cli.py](src/rag_cli.py) запрашивает ближайшие чанки из Chroma для `K=3` и `K=5`, чтобы сравнить ответы. [src/rag.py](src/rag.py) принимает `top_k` как аргумент. В интерфейсе K выбирается ползунком; сервер вызывает `similarity_search_with_score(question, k=top_k)`.
3. **Динамический системный промпт.** Найденные чанки нумеруются `[1]`, `[2]` и далее, к каждому добавляются имя книги и PDF-страница. Этот текст подставляется вместо `{context}`. Промпт требует отвечать по фрагментам и сообщать, если в них нет ответа. См. [src/rag_cli.py](src/rag_cli.py), [src/rag.py](src/rag.py) и [rag_server.py](rag_server.py).
4. **Генерация ответа.** `SystemMessage` с контекстом и `HumanMessage` с вопросом передаются модели, созданной через [src/llm.py](src/llm.py). Использован разрешённый заданием облачный вариант: `get_llm()` вызывает Yandex AI Studio. Локальная LLM пока не подключена; вопрос и найденные фрагменты отправляются провайдеру.

Замеры консольных запросов, сравнение Top-K и примеры ответов приведены в [docs/evaluation.md](docs/evaluation.md).

### Пункт 4. Интерфейс, испытания и вывод

- **Интерфейс:** вместо упомянутых в задании Gradio, Streamlit и OpenWebUI создан [Next.js-фронтенд](Frontend/README.md) с [FastAPI-сервером](rag_server.py). Запуск с реальным бэкендом проверен: видны книги, источники, PDF-страницы, параметры Top-K и temperature, время поиска и генерации. Это более объёмная реализация интерфейса; если перечисленные инструменты обязательны, соответствие формальному условию нужно согласовать с преподавателем.
- **Три вида вопросов:** ответ по книге Девлин, отказ на вопрос о яблочном пироге и проверка ложной предпосылки о кеше Hugging Face с ответами, источниками и метриками разобраны в [docs/evaluation.md](docs/evaluation.md). 
- **Скриншоты или скринкаст:** снимки интерфейса собраны в [docs/screenshots/](docs/screenshots/) и описаны в [отчёте](docs/evaluation.md).
- **Архитектурный вывод:** BGE-M3 выбрана как мультиязычная модель эмбеддингов для русскоязычных книг; Chroma хранит индекс локально. Облачная генерация позволила проверить RAG без развёртывания большой LLM на компьютере. Пока контекст уходит в облако, систему нельзя считать полностью изолированной для корпоративных данных (но я этой цели и не преследовал). Наблюдавшиеся ограничения описаны в [docs/evaluation.md](docs/evaluation.md).

## Как устроена система

Архитектура решения - в /Docs

Обработка книг выполняется при подготовке базы; при вопросе пользователя повторно обрабатывать PDF не нужно.

- `src/config.py` — настройки из `.env`;
- `src/llm.py` — подключение к модели в Yandex AI Studio;
- `src/ingestion/pdf_loader.py` — чтение PDF и сохранённого результата OCR;
- `src/prepare_ocr.py` — однократное распознавание проблемной книги;
- `src/processing/chunker.py` — разбиение страниц на чанки;
- `src/storage/chroma_store.py` — доступ к локальной Chroma;
- `src/index_documents.py` — индексация всех книг;
- `src/search_chunks.py` — проверка базы и семантического поиска;
- `src/rag.py` — функция поиска и генерации ответа для будущего интерфейса;
- `src/rag_cli.py` — консольное сравнение ответов при `Top-K=3` и `Top-K=5`;
- `src/inspect_documents.py`, `src/inspect_chunks.py`, `src/check_embeddings.py`, `src/check_llm.py` — проверки отдельных этапов.



При подготовке корпуса [src/ingestion/pdf_loader.py](src/ingestion/pdf_loader.py) читает PDF, [src/prepare_ocr.py](src/prepare_ocr.py) однократно распознаёт проблемную книгу, [src/processing/chunker.py](src/processing/chunker.py) делит страницы на фрагменты, а [src/index_documents.py](src/index_documents.py) записывает их в Chroma. На каждый вопрос заново обрабатывать PDF не требуется.

При вопросе веб-интерфейс обращается к маршрутам `/api/rag/*` в [Frontend/src/app/api/rag/](Frontend/src/app/api/rag/). Когда задан `RAG_BACKEND_URL`, Next.js передаёт запросы Python-серверу: `/status` и `/documents` читают сведения об индексе, а `/chat` выполняет поиск, формирует промпт, вызывает LLM и возвращает ответ и источники. Если Python-сервер недоступен, интерфейс показывает ошибку без автоматической подмены ответа демонстрационным. **Если `RAG_BACKEND_URL` не задан, включается встроенный демонстрационный режим с примерными данными; для проверки ДЗ нужен реальный режим.**

[src/rag.py](src/rag.py) остаётся самостоятельной функцией одного RAG-запроса, а [src/rag_cli.py](src/rag_cli.py) — консольной проверкой двух значений Top-K. 

Веб-сервер **не импортирует** эти файлы: он повторяет последовательность поиска и генерации, но разделяет с ними [src/llm.py](src/llm.py) и [src/storage/chroma_store.py](src/storage/chroma_store.py). Действующая база — Chroma.

Ответ во фронте приходит как события SSE: категория вопроса, источники, текст и замеры времени. `rag_server.py` сначала дожидается полного `llm.invoke()`, затем отправляет готовый текст частями. Это **не потоковая генерация токенов модели**.

## Корпус и индекс

В корпус входят «Генеративный ИИ на практике» (2026), М. С. Девлин «Построение LLM-агентов с помощью RAG, графов знаний и осмысления» (2026) и В. Дронов «Искусственный интеллект с LangChain» (2026). PDF хранятся локально в `data/raw/private/` и не публикуются в репозитории.

У первой книги текстовый слой неполный, поэтому она распознана Tesseract (`rus+eng`). Результат хранится в `data/processed/private/generative_ai_ocr.jsonl`; остальные две книги читаются напрямую через PyMuPDF. Каждый непустой документ сохраняет имя файла и **номер страницы PDF**, который может отличаться от печатного номера. OCR иногда искажает код и латинские символы, поэтому примеры кода следует сверять с указанной страницей оригинала.

В проверенном запуске получено **961 непустая страница из 987**, **1 989 801 символ** и **2850 чанков**: 1070, 599 и 1181 по книгам соответственно. Используется `RecursiveCharacterTextSplitter` с `chunk_size=1000` и `chunk_overlap=150`. Чанки с источниками, страницами и стабильными ID находятся в локальной Chroma (`data/chroma/`); размерность векторов BGE-M3 — 1024. Это результаты конкретной индексации, а не значения, записанные в интерфейсе: статус сервера читает текущую базу.

## Установка и подготовка базы

Нужны Python 3.12, `uv`, Node.js с `npm`, три PDF корпуса и Tesseract с языками `rus` и `eng` для первого OCR. Из корня репозитория установите Python-зависимости и создайте конфигурацию:

```bash
uv sync
cp .env.example .env
mkdir -p data/raw/private
```

В корневом `.env` задайте свои `YC_API_KEY`, `YC_FOLDER_ID` и `YC_MODEL_ID`. Поместите PDF в `data/raw/private/`. Если база ещё не подготовлена, запустите по порядку:

```bash
uv run python -m src.check_llm
uv run python -m src.prepare_ocr
uv run python -m src.inspect_documents
uv run python -m src.inspect_chunks
uv run python -m src.check_embeddings
uv run python -m src.index_documents
uv run python -m src.search_chunks
```

OCR и индексация нужны при подготовке или обновлении корпуса. Для обычного вопроса повторять их не требуется. Консольная проверка RAG из пункта 3:

```bash
uv run python -m src.rag_cli
```

## Запуск веб-интерфейса

Подробности устройства и возможностей фронта: [Frontend/README.md](Frontend/README.md).

Используются **два терминала**. В первом, из корня проекта, запустите бэкенд:

```bash
uv run uvicorn rag_server:app --port 8000 --reload
```

Для быстрой проверки откройте `http://127.0.0.1:8000/status`: при доступной базе там будет `"connected": true` и реальные числа книг и чанков. `/health` подтверждает только работу HTTP-сервера, а не состояние Chroma.

Во втором терминале, из корня проекта, установите зависимости фронта и создайте файл `Frontend/.env.local` с одной строкой `RAG_BACKEND_URL=http://127.0.0.1:8000`. Этот файл игнорируется Git. Затем запустите Next.js:

```bash
cd Frontend
npm ci
npm run dev
```

Откройте `http://localhost:3000`. После установки зависимостей для следующих запусков достаточно `npm run dev`. Если `.env.local` создан или изменён при уже работающем Next.js, перезапустите фронт. Терминалы с обоими серверами оставьте открытыми.

### Работа с интерфейсом

- **«Новый диалог»** создаёт отдельный чат; последующие вопросы добавляются в текущий. Слева можно вернуться к старым чатам, открыть их ответы, переименовать или удалить диалог.
- **«Параметры»** справа позволяют выбрать Top-K (1–10) и temperature. **«Источники»** показывают найденные фрагменты и PDF-страницы; под ответом доступны замеры поиска и генерации.
- История чатов и ответы сохраняются средствами [Zustand persist](Frontend/src/store/chat-store.ts) в `localStorage` **этого браузера**. Они переживают обновление страницы, но не синхронизируются между браузерами и могут исчезнуть при очистке данных сайта. Сервер  не использует старые сообщения как контекст: каждый вопрос к модели обрабатывается отдельно.
- Для проверки используйте вопрос по книгам, вопрос вне корпуса и сложный вопрос, затем сопоставьте ответ с источниками. Одного бейджа «В корпусе» недостаточно: его категория определяется простым правилом, а не независимой проверкой истинности ответа.

## Приватность и ограничения

`.env`, `Frontend/.env.local`, PDF, OCR-результаты, Chroma, `.venv`, `node_modules` и `.next` исключены из Git. BGE-M3 создаёт эмбеддинги локально, а Chroma хранит индекс локально. 

Поиск может пропустить абзац с ответом даже при наличии его в PDF; увеличение Top-K иногда помогает, но не гарантирует точность. Отказ на вопрос вне корпуса зависит от найденного контекста и поведения модели. Подробные наблюдения и примеры: [docs/evaluation.md](docs/evaluation.md).
